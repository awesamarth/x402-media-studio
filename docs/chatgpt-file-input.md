# ChatGPT attachment integration contract

Official reference: https://developers.openai.com/plugins/reference#file-apis (checked October 17, 2026).

ChatGPT supports native file inputs on a directly registered tool descriptor through `_meta["openai/fileParams"]: ["file"]`. The top-level `file` schema must declare `download_url`, `file_id`, `mime_type`, and `file_name`; only `download_url` and `file_id` are required. ChatGPT supplies the authorized temporary download URL. This is a supported alternative to routing video bytes through model-generated JSON/base64. A direct Media Studio ChatGPT MCP integration could receive that file, enqueue bounded acquisition on the backend, then retain the request handle/asset ID internally and hand the quoted purchase URL to PayBox. No separate upload webpage is necessary for that architecture.

This is NOT yet an implemented or verified route in the current PayBox bundle. The callable PayBox `use_plugin` tool has `plugin_id`, `tool_id`, nested `input`, optional `invocation_id` and `wallet_id`; it has no top-level native file argument or advertised `openai/fileParams`. PayBox's public hosted-plugin guide does not document propagation of file metadata or authorization from a nested plugin tool through this wrapper. Do not invent a file download URL, treat an opaque attachment ID as a URL, or claim adding a nested JSON property alone grants attachment access. Enabled plugin tools may be separately exposed by a host; their actual descriptor must be inspected before claiming they preserve native file metadata.

To implement the supported direct route, expose a ChatGPT-compatible MCP tool with the native descriptor, connect it as its own app, receive an actual authorized file reference, and verify bounded backend download (public-address-only HTTPS, no redirects, size/time limits, temporary URL kept out of logs), raw upload and quote. PayBox remains the payment provider. That app connection/host transport has not been established in this project. The existing raw-byte endpoint remains verified for agents that already possess bytes and outbound HTTP capability. Current deployment does not accept arbitrary attachment URLs.

## Implemented direct endpoint

`https://x402-media-studio.awesamarth.dev/mcp` now exposes prepare_video (native fileParams), get_video_input, get_media_purchase, get_media_job and read_media_artifact. It supports legacy stateless 2025 MCP and modern SDK handling. It returns input preparation immediately; acquisition runs on the backend with one active attachment at a time, 100 MiB/90-second bounds, HTTPS public-address pinning, certificate validation, allowed OpenAI file hosts and no redirects. Signed URLs are not persisted or returned. Inputs inherit existing media validation, requests, ownership, quote pricing and file retention. No file bytes go through PayBox or model-generated base64.

A live HTTPS tools/list confirmed all five tools and exact metadata/schema. A focused local MCP call using injected known fixture bytes completed actual media upload and quote (ready, 10000 atomic USDC) without payment. This does not prove a real ChatGPT attachment arrived. Brave connection form is prepared, but final persistent connection creation awaits action-time user approval. No new connection has been granted yet. The previous section describing the missing implementation is historical; the remaining unverified step is host connection and real file delivery.
